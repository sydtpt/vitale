## Hypotheses checked
- **H1 Core AI on iPhone faster or leaner than MLX or Core ML for the same model — PARTLY / not established.** Decode: Gemma 4 E2B Core AI 46.9 cold vs MLX 44.1 cold vs LiteRT 55.4 vs llama.cpp 38.5 (roughly MLX-level, below LiteRT); Qwen3 0.6B Core AI GPU 193.3 cold vs MLX 178.8 warm (+8%, but June vs July runs); Core AI ANE 122.4 vs Core ML ANE 37.7 (different recipes and dates); Mac M4 Max Qwen3 0.6B 503 vs 432 (+16%). Latency to first token is far worse for Core AI on E2B (3,133 ms vs 218 ms MLX), plausibly the #201 S=1 prefill bug. "Leaner": 455 MB vs 3.0 GB is not a fair comparison (footprint metric, mmap). No Core AI number for any diffusion or segmentation model exists in the evidence. Independent Core AI ≈ Core ML parity for YOLO26n (earlier round, Ultralytics PR) points the same way for small vision nets. Confidence M, single-author bench.
- **H2 Sustained GPU inference throttles substantially within minutes while the ANE holds up — PARTLY CONFIRMED (LLM decode only).** Same phone, same model: MLX keeps 38%, LiteRT 48%, Core ML/ANE 67% after 10 minutes; −25% arrives at 35–40 s for the GPU runtimes vs 390 s for the ANE. arXiv 2603.23640 independently shows an iPhone 16 Pro losing nearly half its throughput within two iterations on GPU-class inference. Overstatement to avoid: the ANE also lost a third, the ANE run is a different (sliding-window) workload, the power mechanism was measured on a Mac, and the −10% at 5 s for MLX suggests a fast governor step, not only slow heat soak. For an imaging pipeline (one 10–40 s burst per photo) the risk is back-to-back batches; Imarello also reports thermal pressure at 1024². No diffusion sustained-load data exists.
- **H3 Core ML is not deprecated in iOS 27 (Apple source needed) — NOT FOUND.** Three Apple pages read (sessions 324, 326, WWDC26 ML guide): no statement in either direction; the guide has no Core ML session. Soft signals that Core ML is de-emphasised: no Core ML session, coremltools' latest shown release targets iOS 26 with no Core AI mention (L, dates inferred), Apple's new converter is `coreai-torch`. Soft signals that it still works: it ran on iOS 27 in the bench and ExecuTorch 1.5.0 (2026-09-16) still ships a Core ML library. Media call Core AI a "successor"/"replacement" (not Apple). Answer cannot be given from an Apple source this round.
- **H4 MLX runs image-generation models on iPhone in a shippable way — PARTLY.** It runs: mlx-swift-examples' StableDiffusionExample targets iOS, and Imarello runs FLUX.2 Klein 4B 4-bit on an iPhone 17 Pro at 512² in 9.9 s with 2.6 GB peak (37.4 s / 2.98 GB at 1024²), comfortably inside a 12 GB device. Not shown shippable: experimental profile, no release, not on the App Store, thermal pressure at 1024², Low Power Mode and lifecycle gating pending, weights need resync after install, and no img2img/inpaint/ControlNet number. Confidence M-L (one project).

## Recommendation — which runtime for which stage (evidence-graded)
Segmentation (stage 1): Apple's own showcase is SAM 3 through Core AI (S5, iOS 27.0 target), but there is **no iPhone latency or memory number** for it anywhere in this round (grade: L for performance, H that Apple promotes it); models this size make the runtime choice second-order, so keep a Core ML/Vision-class fallback behind one Swift protocol. Diffusion (stage 2): the only measured iPhone 17 Pro image-generation figures are **MLX FLUX.2 Klein 4B 4-bit (512²: 9.9 s, 2.6 GB peak; grade M-L, single project, text-to-image only)**; Core AI has a FLUX.2 iOS path but no published numbers, an open MPSGraph heap bug on another model and a hang bug that was fixed only on 2026-09-19, so treat it as the target to benchmark, not the default (grade M). Whichever engine wins, plan for one model stage resident at a time (Imarello's pattern) and for thermal pauses between photos: LLM data on the same phone shows GPU runtimes losing 52–62% in 10 minutes (M), which matters for batches, not a single 10–40 s render. Recomposition, colour harmonisation and the overlay (stages 3–4) need no ML runtime and were outside this round. Preset choice (stage 5): rules or a sub-1B model; the LLM evidence (Qwen3 0.6B at 120–190 tok/s, ~0.5 GB) means any of LiteRT-LM, MLX or Core AI would do, so use whatever engine stage 2 already loaded, and consider Apple's Foundation Models framework (its WWDC26 listing mentions multimodal image prompts; not verified here) to avoid shipping weights. Nothing here supports a memory-limit conclusion: no Apple per-process number, no jetsam guidance in sessions 324/326.
