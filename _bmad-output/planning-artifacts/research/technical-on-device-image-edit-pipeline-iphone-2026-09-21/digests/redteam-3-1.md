## Strongest counter-argument

"Sound primary runtime today" bundles three stages that fail differently, and the evidence is worst exactly where the plan is most ambitious. For diffusion, the only FLUX.2 Core AI port I found says it is macOS-only because ~6.5 GB peak beats a 12 GB iPhone's ~6.1 GB process limit, so "FLUX.2 on iPhone via Core AI" is not a runtime choice, it is a model-size problem that no runtime fixes; you are down to SD-class ~1B models, where Core ML already has years of iPhone-proven recipes. For the LLM/VLM stage, the same repo's open issues describe silent corruption on iOS specifically (static-shape export garbled, KV >= 2048 garbage, multi-token prefill crashing in MPSGraph), with a 1,024-token iOS context ceiling and no Apple replies in the threads, and the one production vendor that shipped Core AI on iOS 27.0 (Ultralytics) found FP16 wrong outputs and process-killing ANE assertion failures on iPhone 17 Pro, measured Core AI only level with Core ML, and kept Core ML as the default. The community's own tooling assumes conversions are "quietly wrong" until gated (64 rules). Add no simulator, no external PRs, and a beta-to-beta export change that made the same recipe 2.2x slower, and the honest reading is "promising accelerator behind a verification gate", not "primary runtime".

## Verdict

Does not survive as worded; a narrower version does. Survives: for a small LLM and SAM 3 on a recent iPhone, Core AI is plausibly the fastest option and has an official iOS path (I saw SAM 3 int4 per-channel ~3 GB to ~430 MB split into image_encode / text_encode / detect; Qwen3-0.6B ~1.6x MLX decode on iPhone 17 Pro, same-session). Must be revised: (1) drop FLUX.2 as an iPhone Core AI target; plan SD-class (~1B) diffusion, or keep diffusion on Core ML, or offload; (2) replace "primary" with "primary candidate, Core ML/MLX fallback retained" and add a per-model, per-OS-build golden-output gate on a physical device (FP32/CPU reference vs default placement) because FP16 default-specialization output was wrong on iPhone 17 Pro / iOS 27.0; (3) cap iOS LLM context at <=1,024 tokens and force dynamic-shape exports where possible; (4) budget device-only CI and pin the toolchain (coreai-torch >= 0.4.1, Xcode 27.0, one OS build) because export lowering has changed performance 2-4x between betas; (5) treat "small LLM faster than MLX" as a burst, single-session number until a sustained/thermal run exists for Core AI.

- Counter-evidence to the bear case, for balance: Core AI beat Core ML on detect and classify (3.73 vs 4.59 ms; 1.19 vs 1.98 ms) and beat MLX on tiny-model decode; an official SAM 3 iOS path exists.
