## Hypotheses checked

- **H1 "Gemma 4 E2B exists and has an iPhone-ready build" — CONFIRMED (with a runtime caveat).** Exists (#11, Apache-2.0 per card summary). iPhone-ready via Google's **LiteRT-LM**, with published iPhone 17 Pro numbers (#12: GPU 56 tk/s decode, TTFT 0.3 s, 1450 MB peak; 2.58 GB file). **Not** in Apple's Core AI recipe list (#13 shows Gemma3/3n only), so it would NOT plug into `CoreAILanguageModel`. React Native/Swift binding of LiteRT-LM not checked. Numbers need a 2nd source.
- **H2 "Qwen3.5-2B has an iPhone-ready build in Core AI recipes" — NOT FOUND / overturned as stated.** Qwen3.5-2B exists (#14, Apache-2.0). The Core AI listing shows Qwen2/2.5, Qwen3 (+MoE), Qwen3-VL, not Qwen3.5 (#13; verify by re-reading the tree). iPhone builds of Qwen3.5 seen only as GGUF/llama.cpp in a promo blog (#15, L). MLX Qwen3.5 exists for Mac (snippet only). Nearest Core-AI-ready sibling: **Qwen3 (0.6B example in the repo's own CLI docs)**.
- **H3 "Foundation Models guided generation reliably returns a valid enum case" — PARTLY; not evidenced this run.** Evidence: `@Generable` and a `.guidedGeneration` capability exist; the framework hands the schema to the executor (#5). My prior belief (unverified this run) is that the system model's `@Generable` output is schema-constrained by design, so "valid case" would hold structurally; but I retrieved no primary statement of that, and for **third-party executors validity depends on the provider's implementation** (#5). "Picks the *right* case" (semantic accuracy) — no evidence at all (#20). Cheap mitigation regardless of rung: validate the id in code and fall back to rules.
- **H4 "Deterministic rules are enough for 4–6 presets" — PARTLY (analysis, not evidence).** For metadata-only inputs (distance, elevation, hour, weather, effort) a decision table over 4–6 classes is exhaustively testable and I found nothing suggesting an LLM adds value. With the corrected premise (photo content matters) metadata rules cannot see scene/sky/light; rules need pixel-derived inputs (luminance, colour temperature, sky share — cheap and deterministic) or a small vision classifier. No source compared rules vs LLM (#20).

## Recommendation ladder (when each rung earns its cost)

1. **Rung 0 — rules + cheap pixel statistics (build first, keep forever as fallback).** Cost: zero download, zero load, deterministic, unit-testable. Earns its place immediately for anything metadata can decide (time of day, weather, effort, distance/elevation → preset). Add 3–5 photo features computed in Swift/Metal (mean luma, luma histogram spread, colour temperature/tint, saturation, blue-sky/upper-region fraction) to cover much of "scene/light" without a model. Insufficient alone for semantic content (food vs landscape vs people vs pet) — but whether presets even differ by that is a product question, not a research one.
2. **Rung 1 — Foundation Models, one call: photo `Attachment` + metadata string → `@Generable` enum + a few `@Guide`-ranged numbers.** Evidence for: iOS 27 system model takes images and has an 8192 window (#1, #2); no model to ship, download or load into your process budget (the framework/OS owns it — memory not documented, so measure). Earns its cost when the photo *meaning* changes the preset and rules cannot see it. Conditions to verify before relying: Apple-Intelligence-eligible device/region/user opt-in (not verified this run), image-token cost against 8192 (undocumented — downscale the image), semantic accuracy (no evidence — build a 30–50 photo golden set), and always validate the id and fall back to rung 0. Log rung 0 vs rung 1 agreement to learn whether rung 1 is worth keeping.
3. **Rung 2 — dedicated zero-shot scene classifier (CLIP-family), only if rung 1 is unavailable/inconsistent.** One image-encoder pass + precomputed text embeddings for ~20 scene prompts → features into rules. Tens to low hundreds of MB, no generation, no enum problem at all. MobileCLIP2 is the natural pick technically but its weights are reported research-only (#18) — a publishing blocker unless the TOU says otherwise; check the Core AI `CLIP` recipe's weight source and licence, or SigLIP-class alternatives (unverified).
4. **Rung 3 — open small VLM/LLM (Gemma 4 E2B via LiteRT-LM, Qwen3/Qwen3-VL via Core AI).** Earns its cost only if you need free-text reasoning (e.g. reading an activity title/notes) or must support devices where rung 1 is absent AND rung 2 is not enough. Cost: 2.6 GB+ download, ~1.45 GB GPU peak for E2B (vendor number), unmeasured load time, and one more heavy model to sequence against diffusion. For a 4–6-way choice this is the least defensible rung. If used, a grammar/schema-constrained decode is required for validity (#5, #16); on `CoreAILanguageModel` whether the constraint is grammar-enforced is unverified (#6).

## Better options not on the brief's list (unverified unless stated)

- **Apple's own on-device vision classifier** (Vision framework image classification, `VNClassifyImageRequest` / newer Swift `ClassifyImageRequest`): OS-resident, no model to ship, returns scene labels (sky, sunset, food, people…). From prior knowledge only — **not evidenced this run; highest-value single lookup for the next round** because it may make rungs 2–3 unnecessary.
- **Core AI `CLIP` recipe** (#13) as the zero-shot classifier if its weights licence permits.
- **Newer Qwen (3.6–3.8) small sizes** — a "3.5 to 3.8" guide and a Qwen3.8 HF repo surfaced (#14); small sizes/iOS builds unchecked.
- **FM `@Generable` with the 20B "Core Advanced" tier** — only if third-party access is real (#9, unverified).
