### T3 — Per-process memory ceiling
- Apple's entitlement doc: "A Boolean value that indicates whether core features of your app may perform better with a higher memory limit on supported devices."; "An increased memory limit is only available on some device models."; call `os_proc_available_memory` to check; listed iOS 15+/iPadOS 15+/visionOS 2.5+; NO numeric limit anywhere | https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit (read through the sosumi.ai mirror) | Apple | n/a | H | memory | no
- Apple DTS engineer (forum thread, Nov 2023, iPhone 8 / iOS 15.2): the docs "are deliberately vague"; "the exact behaviour you see depends on the device type, the OS version, and the state of the device"; "make sure your app still behaves correctly if additional memory isn't available". Gives no number. Stale (2023) but it is Apple's own stated stance | https://developer.apple.com/forums/thread/740831 | Apple DTS | 2023-11 | H (stale) | memory | no
- VERDICT on "~6.1 GB per-process limit": no source found. Apple documents no number and says it is deliberately vague and varies by device/OS/state. Treat 6.1 GB as folklore until someone logs `os_proc_available_memory()` on an iPhone 17 Pro. The only measured working-set datapoint anywhere (round 1, unverified): 3.65 GB model -> 4.65 GB peak with the entitlement. Practical rule from Apple's text: read `os_proc_available_memory()` at runtime before each model load and degrade (smaller resolution, `--low-memory` tiled VAE, single-function) instead of assuming a constant.

## Hypotheses checked
- H1 (Core AI ships iOS-capable recipes for SAM 3, FLUX.2 Klein 4B img2img, SD img2img, EDSR, LLM/VLM in one format) — PARTLY CONFIRMED. Verbatim in primary READMEs: one `.aimodel` format; SAM 3 with an iOS-recommended 336 lite export and text prompts; FLUX.2 with iOS preset (512, single-function, half reference grid) and img2img via reference tokens; SD 1.5/2.1/3.5-Medium "Yes" on iOS with a VAE encoder for 1.x/2.x; LLM recipes evidenced by issues (Gemma 3, Gemma 4 E2B on iOS 27). NOT verified: EDSR, efficient-sam, depth-anything, any VLM (READMEs unread); "Klein 4B" (not restated). Caveat: "iOS-capable recipe" is not "measured running on an iPhone within memory"; open iOS bugs (#257, #124, #201) and recently fixed ones (#235 blank SD-1.5, #129 SD-2.1 garbage, #230 Flux2 loader hang on 2026-09-19) show the iOS path is young.
- H2 (no ControlNet/inpainting in the diffusion recipes) — NOT FOUND, consistent (needs-2nd-source). Neither the FLUX.2 nor the SD README returned any ControlNet/inpainting/LoRA text, and no issue title on page 1 mentions them; but the `models/` directory list was never enumerated and only the first issue page was seen. FLUX.2's reference-token conditioning is the recipe's native structure/identity-preserving edit path.
- H3 (a ~4 B diffusion transformer runs on iPhone 17 Pro within its memory limit) — UNRESOLVED, plausible. For: Apple ships an explicit iOS preset built "to limit peak memory" (single-function, 512, half grid, tiled low-memory VAE) and quotes "~2 GB" transformer artefacts; round-1 Zenn datapoint (unverified) shows 4.65 GB peak reachable with the entitlement. Against/unknown: zero measured FLUX.2-on-iPhone number (latency, peak, load time) in anything retrieved; the per-process limit is undocumented; multi-component sequencing (text encoder -> transformer -> decoder, plus SAM 3 and a small LM) must fit under an undocumented ceiling; first-load specialisation is slow and must not happen in an interactive flow.
- H4 (GPU/ANE inference is foreground-only on iOS) — PARTLY OVERTURNED for GPU, UNKNOWN for ANE. iOS 26+ `BGContinuedProcessingTask` + background-GPU capability allows GPU work after backgrounding "on supported devices", but only if user-initiated, progress-reporting, with an expiration handler, and the system may throttle/suspend/terminate; iPhone support must be queried at runtime and the retrieved text does not confirm it. Nothing retrieved says whether Core ML/Core AI Neural Engine work runs in that mode. Default design: treat the pipeline as foreground, and use a continued-processing task only as a best-effort extension.
