### T1 — Expo Modules API, local modules, SwiftPM
- Swift `AsyncFunction` returns a JS promise. Its native body runs on a different thread than the JS runtime by default. `.runOnQueue(.main)` changes the queue. The docs recommend it for I/O-bound work, work "needing to run on a different thread" and "extensive or long-lasting" operations. | https://docs.expo.dev/modules/module-api/ and https://raw.githubusercontent.com/expo/expo/main/docs/pages/modules/module-api.mdx | Expo | n/a (main branch) | H | capability | no
- Events: `Events("onX")` declares them; `sendEvent("onX", payload)` emits; `OnStartObserving("onX")` / `OnStopObserving("onX")` are scoped per event for setup/teardown. | same | Expo | n/a | H | capability | no
- Lifecycle hooks: `OnCreate`, `OnDestroy`, `OnAppEntersBackground`, `OnAppEntersForeground` (iOS-only; Android has `OnActivity*`). | same | Expo | n/a | H | capability | no
- File handling: the built-in `URL` convertible takes a string ("when a scheme is not provided, it's assumed to be a file URL"). `Data` maps to `Uint8Array` (SDK 50+). So file-URI-in / file-URI-out is native to the API, and the byte-array path exists but is the wrong choice for multi-MB images. | same | Expo | n/a | H | capability | no
- Cancellation / concurrency: the only cancellation statement is Kotlin's ("all unfinished suspend functions will be canceled when the module is deallocated"). The reference page has NO Swift `Task`, `async/await` or `@MainActor` guidance and no `SharedObject`/`SharedRef` section. Therefore Swift-side cancellation (a jobId -> Task registry) is app-owned design, not a documented pattern. | same | Expo | n/a | M (absence, summarised fetch) | capability | yes
- PR expo/expo#50329 "[ios][expo] Declare a pure-Swift module's SwiftPM package dependencies" is OPEN (opened 2026-09-18, three days ago; author chrfalch, Expo). ### T3 — Orchestration on a memory ceiling, caches
- Core AI (iOS 27): "specialization" compiles a model for the device (segment, plan, optimise compute; executable artifacts generated for the compute units used). On load the framework checks whether the model is already specialised and cached; later loads come from the cache and are fast. `AIModelCache` lets you delete entries and set persistence policy, and a cache can be shared between apps in one app group. Models are "automatically specialized for the hardware they run on", and ahead-of-time compilation is supported for quick loads ("Compiling Core AI models ahead of time"). `.aimodel` bundles on iOS 27 / macOS 27. No timings or cache-key details retrieved. | https://developer.apple.com/videos/play/wwdc2026/324/ , /326/ , /325/ ; https://developer.apple.com/documentation/coreai/compiling-core-ai-models-ahead-of-time (search summary; pages not opened) | Apple | 2026-06 | M | capability | yes
- Core ML (older runtime): `.mlpackage` recompiles for the Neural Engine on every load (README: 2-3 minutes); `.mlmodelc` caches the compiled asset and later loads take seconds; the cache entry is tied to the full file-system path of the .mlmodelc folder. Apple's README data is 2022-23. | https://github.com/apple/ml-stable-diffusion (fetched); https://apple.github.io/coremltools/docs-guides/source/model-prediction.html (search summary) | Apple | 2022-23 | M | perf | yes

## Hypotheses checked
- H1 (single Swift Expo module: `start(job)` / events / `cancel(jobId)`, file-URI in and out) — PARTLY. Every primitive is documented: off-JS-thread `AsyncFunction`, `Events`/`sendEvent`, file-URL convertible, lifecycle hooks including `OnAppEntersBackground`. No source calls this shape "recommended", and Swift `Task` cancellation is undocumented on the reference page (Kotlin coroutine cancel-on-dealloc is the only documented cancellation), so the jobId -> Task registry and cooperative cancellation checks between stages would be our own design. The shape is well supported by the API; "recommended for long native ML jobs" is not evidenced. Also not found: any Expo statement about keeping a module alive through long jobs.
- H2 (full unload returns memory to baseline reliably enough to chain 3 models) — PARTLY / NOT PROVEN. Evidence for the pattern: Apple's own Core ML SD pipeline ships a sequential load/unload mode for iOS at about +2 s (2022-23, old hardware). Draw Things' partial-weight offloading is weaker (L, unopened). Evidence against or missing: no retrieved measurement of residual memory after unloading a Core ML, Core AI or MLX model on any iPhone, and nothing on iOS 27. Treat as an assumption to be measured (per-stage high-water mark and post-unload baseline on the target phone) before committing the architecture.
- H3 (ANE/Metal specialisation paid once per model + OS version, cached on disk) — PARTLY. Confirmed that Core ML `.mlmodelc` caches the specialised asset on disk keyed to the model path, and (Apple WWDC26 pages, search summary) that Core AI specialises on first load and serves later loads from `AIModelCache` with a persistence policy and app-group sharing. NOT confirmed: that the cache key includes OS version (only speculative wording seen), first-load durations for diffusion-scale models, `.mlpackage` vs `.aimodel` behaviour when the path changes (a re-downloaded asset pack could land at a new path), and whether MLX/Metal shader compilation is cached. AOT compilation exists as the documented escape from first-run cost; whether the AOT artifacts are per-chip is unverified.
