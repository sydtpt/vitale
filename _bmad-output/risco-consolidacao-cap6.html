Risco da Consolidação CAP-6

Vinte e cinco commits moveram 139 chamadas .from() para dezesseis módulos de dados com dono único. As três suítes ficaram verdes, o build passa, os dados de produção estão sãos — e ainda assim um bug de leitura chegou ao usuário. Este documento explica por que isso era inevitável com a cobertura atual, e o que fecha a lacuna.

Veredito

CONCERNS passa para uso pessoal · reprova como base para a próxima migração

A consolidação está estruturalmente correta e o architecture.test.ts faz o que promete. O problema não é o que foi movido — é que a camada para onde tudo foi movido não tem nenhum teste. O achado F1 pontua 9 na matriz de risco (probabilidade 3 × impacto 3), o que exige mitigação documentada antes da próxima mudança de dados.

Por que 479 testes não pegaram

Não é uma lacuna de quantidade. É uma lacuna de camada, e ela é total.

Nenhum dos 479 testes importa um store ou um módulo de dados. Verifiquei arquivo por arquivo: os .spec.ts do web vivem em features/*/data/ mas cobrem apenas os agregadores puros — overview, type-summary, country-explorer, weekly-load. No mobile, as 29 suítes cobrem lib/: mapeamento, dedupe, zonas de FC, formatação. Zero mocks de AuthService. Zero mocks de useAuthStore. Zero SupabaseClient falso.

A consolidação moveu exatamente a camada que ninguém testa. Uma suíte de funções puras não pode, por construção, observar uma query — e portanto passa igual se a query pedir a coluna errada, filtrar pelo campo errado ou nem rodar.

O architecture.test.ts reforça essa falsa sensação de segurança, e vale entender por quê: as quatro barreiras verificam onde a query mora, nunca o que ela pergunta. Elas garantem que nenhum .from() escape do núcleo. Nenhuma delas olha para dentro do select().

A melhor evidência disso está na própria mensagem do commit 8c0837d: o SELECT do web omitia source_id e device, e a linha "Dispositivo" da tela de detalhe nunca aparecia. Esse bug viveu no repositório com a suíte verde o tempo todo, e foi encontrado a olho, durante a migração. Como você mesmo escreveu lá: uma coluna a menos no SELECT é uma feature morta sem aviso. É a mesma classe de falha do mapa.

Achados

Pontuação = probabilidade × impacto, escala 1–3 cada. ≥ 6 exige mitigação; 9 bloqueia.

F1

A camada de I/O tem 0% de cobertura — e agora concentra tudo

Dezesseis módulos em packages/shared/src/data/, 90 funções exportadas (76 delas assíncronas, tocando o banco), servindo os dois apps. Antes, um erro de query afetava uma tela; agora afeta todas as que compartilham o módulo. A consolidação aumentou o raio de explosão de cada defeito sem adicionar nenhuma rede de proteção proporcional.

F2

Mobile envenena o cache de rotas quando não há sessão

Em activities.store.ts:211, se uid for falsy o bloco try inteiro é pulado sem erro, e o loop seguinte grava [] para todos os ids. O guard de refetch é cache[id] === undefined — e eles deixaram de ser undefined. O mapa fica vazio até o app reiniciar, mesmo depois de a sessão resolver. O web lança exceção no mesmo ponto; o mobile falha em silêncio, que é pior.

Alto · 6TECHProb 2 × Imp 3mobile/src/store/activities.store.ts:211
F3

Noventa e cinco pontos de decisão, três políticas de falha diferentes

O mesmo if (!userId) se resolve de três formas incompatíveis conforme o arquivo: throw new Error('Sessão não encontrada.'), return silencioso, ou _error.set(...) com estado de erro. Dentro de um único store as três convivem — activities.store.ts do web usa estado de erro no load() e throw nos outros quatro. Quem chama não tem como saber qual esperar, e o return silencioso não deixa rastro nenhum.

Médio · 4TECHProb 2 × Imp 2web ×35 · mobile ×60
F4

A página de país marca a chave antes de saber se o fetch deu certo

Em activity-country-page.component.ts:130, this.routesKey = key é gravado antes da chamada. Se fetchRoutes falhar, o catch zera as rotas mas a chave permanece — e o effect nunca mais tenta, porque a comparação na linha 129 corta. Qualquer falha transitória vira permanente até navegar para fora e voltar.

Médio · 4TECHProb 2 × Imp 2activity-country-page.component.ts:130
F5

Código órfão sobreviveu à migração no store do web

SELECT (linha 16), DbActivityRow (19–42) e mapRow (191–216) continuam no arquivo, já substituídos por ACTIVITY_COLUMNS e toActivity no shared. O SELECT órfão é a versão antiga — sem source_id e device. Deixá-lo ali é convidar alguém a consertar o lugar errado.

Baixo · 1TECHProb 1 × Imp 1web/.../activities.store.ts

Sobre o mapa: o que não consegui confirmar

Não reproduzi a falha do mapa, e não vou apresentar hipótese como diagnóstico. Levantei uma — corrida com o auth assíncrono — e ela não sobreviveu à verificação: o profileGuard checa a sessão na linha 13 antes de liberar a rota, então quando a página do mapa monta, auth.user() já está preenchido. Os dados de produção também estão sãos e o build passa.

O que resta como suspeita razoável, em ordem: (a) o evento INITIAL_SESSION do supabase-js zerando session transitoriamente depois do guard, que combinado com F4 trava o mapa vazio de forma permanente; (b) a falha estar no mobile, onde não há guard equivalente e F2 é diretamente alcançável.

O que discrimina entre elas, em um minuto: abrir a tela, ver se o erro Sessão não encontrada. aparece no console, e se a requisição a activity_routes chega a sair na aba de rede. Sem essa observação, qualquer conserto é chute — e F1 é justamente a razão de não haver um teste que responda isso por você.

Plano de teste

Ordenado por risco coberto por hora investida. O nível mais baixo que pega o defeito é sempre o preferido.

P0 fecha F1; P1 fecha F2–F4; P2 é rede de segurança.
#TesteNívelPega
P0 Contrato SELECT × modelo. Um teste puro que compara as constantes de coluna de cada módulo de dados com as chaves que o mapeador produz, e ambas com o schema. Falha quando alguém tira uma coluna do select(). unit A classe exata do bug source_id/device
P0 Módulos de dados com SupabaseClient falso. Um duplo que registra tabela, colunas e filtros. Afirma que fetchRouteOverviews lê route_overview e nunca points — a regra que o cabeçalho do módulo documenta e nada verifica. unit Regressão de query nos 16 módulos
P1 Stores com auth não resolvido. Para cada store com cache: chamar com sessão nula, resolver a sessão, chamar de novo, e afirmar que a segunda chamada busca de verdade. integration F2 e F4 diretamente
P1 Barreira de política de falha. Estender architecture.test.ts: todo if (!userId) em store resolve pela política declarada. Barreira estrutural, no espírito das quatro que já existem. unit F3, e impede recaída
P2 Smoke E2E na rota do mapa. Interceptar activity_routes antes de navegar (network-first), afirmar que o traçado renderiza. Um teste, só o caminho feliz. e2e Regressão de ponta a ponta

Uma observação sobre sequência: P0 não depende de nenhuma infraestrutura nova — são testes puros com um duplo de client, no mesmo estilo do que já existe. É o melhor retorno disponível, e sozinho já teria pego o bug que o commit encontrou a olho.
